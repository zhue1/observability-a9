I verified the todo-service on Node.js 22.22.3 with MongoDB 7.0 and Jaeger 2.5.0 running through Docker Compose. MongoDB passed its health check and ping, and the Jaeger UI returned HTTP 200. I first ran console tracing: GET /todo returned three records, and the terminal displayed HTTP, Express, and MongoDB spans, JSON logs, and request metrics. I then switched to the OTLP HTTP exporter on port 4318.

All nine traffic checks passed, covering health, listing, lookup, creation, validation, missing data, and an intentional failure. Jaeger search returned nine todo-service traces. The captured GET /todo trace (fa7791a) contained eight spans and lasted 7.916 ms. Its hierarchy connected the HTTP server span to the Express request handler, the custom todo.list span, and MongoDB's find todos client span. The database span lasted 5.810 ms, about 73% of the total trace duration, identifying database work as the largest measured component in this request. Its attributes identified the todos collection, observability_a9 database, and find operation. This single local request is not a performance benchmark.

The intentional /error-demo request returned HTTP 500. Jaeger showed seven spans with three error-marked spans and recorded the exception. The terminal request counter totaled nine requests, grouped by method, route, and status. For the two successful GET /todo requests, the latency histogram recorded 7.41-10.55 ms, with a 17.96 ms sum and count of two. These application timings differ slightly from the enclosing HTTP span duration because their measurement boundaries differ.

Structured JSON request logs recorded timestamps, status codes, durations, and trace IDs. The GET /todo log matched the captured Jaeger trace ID. Jaeger displayed traces; metrics and logs remained in the Node terminal. Together, these signals showed request flow, aggregate behavior, and correlated application events. Both screenshots were captured from the real local Jaeger UI.
